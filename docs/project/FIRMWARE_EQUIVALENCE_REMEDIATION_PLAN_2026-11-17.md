# PC6M／PC12M 固件逻辑差异消除与缺陷修复实施方案

版本：V1.1；日期：2026-11-17；状态：实施设计，尚未按本方案完成全量验收。

适用项目：PC6M-10、PC12M-2，MCU 为 LPC1765FBD100。

验证范围：仅源码、反汇编、构建产物及模拟执行验证。实机、烧写、接线、仪器测量和带载测试均不在本实施方案内，也不是本方案的验收前提。

## 1. 目标、术语与边界

### 1.1 目标

以各自原始 BIN、原始反汇编和实际执行为证据，系统识别并消除当前源码的非授权逻辑差异；修复由还原错误引入的缺陷；消除调试干预、测试绕过和比较规则不当造成的“假通过”。最终交付可追溯的源码、可复现的测试、差异闭环记录及明确的剩余验证边界。

**“消除”指消除行为差异及验证失真，不是删除代码。** 不以删函数、删分支、删失败样本、删日志或缩小比较范围完成任务。发现异常代码后先核对证据，再修正地址、条件、状态转移、执行环境或比较契约。

“金手指”在本文中指未经有效契约约束、会强制结果或掩盖真实差异的干预，例如强制成功、覆盖业务状态、提前跳过目标路径、用新固件结果充当期望值。该名称不是代码是否应保留的判断依据。

### 1.2 用户已明确的保留项

| 项目 | 处理原则 |
| --- | --- |
| 认证永久放行 | **保留。** PC6M、PC12M原版标志语义不同，分别登记当前放行实现；不得恢复原版认证锁机作为本任务的默认动作 |
| 菜单文字、产品信息、字形及α下标 | 保留已授权定制；单独验证实际显示，不要求定制文字与原厂像素相同 |
| 背光约20秒 | 保留；其它超时不能据此放宽 |
| CRP、向量、启动/链接适配 | 保留已确认的工程适配，逐项记录证据和可观察影响 |
| 原始BIN、反编译、反汇编、硬件资料和过程证据 | 保留；不因“目前未引用”或“发现结论错误”删除，可追加纠正记录 |

上述保留不是允许任意忽略周边差异。例如保留认证放行，不代表可以把启停联锁、急停或故障保护一并强制通过；保留背光20秒，不代表菜单退出计时可以不同。

### 1.3 三类契约

1. **原版兼容契约**：未授权改变的参数处理、状态转移、通信、输出、保护、持久化等，以各自原 BIN 为准。
2. **已授权定制契约**：认证放行、显示和背光等，按明确预期验收；与原版的差异必须限定到具体位置、状态和副作用。
3. **原版自身问题**：若证据表明原版也存在缺陷，不能同时宣称“原版等价”和“改变原版行为”。单列缺陷，说明影响及建议；需要改变控制行为时形成新的明确需求与定制记录。

## 2. 当前依据与证据优先级

### 2.1 原始固件金标准

| 项目 | 文件 | 长度 | SHA-256 |
| --- | --- | --- | --- |
| PC6M-10 | `LPC1765.bin` | 262144 B | `DD629EAC0243A13CECC826B1FC2B4B54066F7647D8C1D09A62D5CAF7B4F13F65` |
| PC12M-2 | `pc12m2_orig.bin` | 262144 B | `2BC608683992AD6DB2D3CB75129BF57EA37D6D681D7C2C0A132E064EBD271BD1` |

比较关系只能是：6M原BIN ↔ 6M新ELF；12M原BIN ↔ 12M新ELF。两项目可以共享方法和用例维度，不能共享未经本机确认的地址、标志极性、寄存器表或通过结论。

证据优先级：原BIN字节与实际执行 → 原始指令及字面量解引用 → 调用点及硬件访问事实 → 当前源码 → 历史说明/反编译伪代码。源码注释出现原地址，不代表地址、位宽或语义已经正确。

### 2.2 已知风险样本，作为实施种子而非完整清单

| 风险类型 | 已发生的实例 | 本次必须扩展的检查 |
| --- | --- | --- |
| 条件缺失 | 参数下限、远程给定上限、retry门控遗漏 | 同类全部分支、阈值前后、状态组合 |
| 数据源错误 | 闭环反馈槽、计数与标志混用 | 两通道、限幅动作、PID入参及后续拍状态 |
| 控制流错误 | 提前return、复位命令返回、共享尾遗漏 | 每个出口、非返回路径、响应和写入顺序 |
| 表达式不等价 | OR与8位加法回绕、符号扩展、索引截断 | 全字节范围、宽度溢出与调用者实际输入 |
| 测试空跑 | 刷新节拍不满足、ADC给定未达到分支门槛 | 执行前种子断言、目标基本块命中及非空观察 |
| 中途状态假一致 | UART未就绪、加载配置超预算仍比较 | 返回门禁、外设模型、预期非返回分类 |
| 观测干扰 | Unicorn内存hook与Thumb IT块交互 | 多种观测方式交叉核对，保留原始差异 |

启动本方案时重新冻结实际HEAD、工作区和构建。历史35/35、8/8及大矩阵结果仅作为历史证据，不自动转移到后续构建，也不代表所有路径已等价。

## 3. 总体路线与执行纪律

依赖顺序：**S0冻结基线 → S1登记契约 → S2修正验证可信度 → S3逐模块对照 → S4定向修复 → S5跨模块连续运行 → S6模拟外设与时序契约验证 → S7交付验收**。

S2未完成的结果可以帮助定位，但不能作为“差异已消除”的唯一验收依据。优先处理保护、输出、反馈、启停和持久化，再处理通信、参数和显示。每项目独立记录完成状态。

执行纪律：

- 保留已有未提交工作。需要稳定版本时创建隔离副本或独立工作树，不强制切分支、回退或清空工作区。
- 原则上一次修复一个可解释的问题或一组同根问题；不要把大规模重命名、注释整理和控制逻辑修复混在同一个补丁。
- 每个修复先保留最小反例；修复前应失败，修复后应通过。若修复前也通过，先证明测试真正覆盖了目标条件。
- 构建后源码、ELF、BIN、测试脚本和日志共同冻结；并行任务改变任一对象后，重判受影响结果，不把混合版本当作一次验证。
- Git提交标题和正文使用中文；提交前检查实际差异和附件，原始板上备份及临时发布包不随源码上传。

## 4. S0：冻结基线与建立可复现环境

### 输入

两个仓库的AGENTS.md、DOCUMENTATION_INDEX.md、现有源码、原始证据、构建脚本、当前未提交差异及历史修复记录。

### 操作

1. 记录项目绝对路径、分支、HEAD及远端；记录工作区差异全文及哈希，标明已提交和待提交内容。
2. 校验原BIN长度与上表哈希；只读使用，不修改原始证据。
3. 分项目冻结当前源码和测试脚本；记录编译器、编译选项、链接脚本、Python及Unicorn版本。
4. 使用项目build.sh重建，记录ELF/BIN哈希、段布局、入口、栈顶、向量校验和及CRP。
5. 记录“当前源码构建”“本次待验镜像”“本次模拟实际加载镜像”，三者不得混写；核对模拟加载内容与manifest哈希一致，不以文件时间猜测版本。
6. 运行当前门禁，保留失败和未完成项；这一轮建立事实基线，不为了报告好看先隐藏差异。

### 交付与门禁

- `baseline_manifest.json`：包含源码/测试/工具版本、原BIN、新ELF/BIN及工作区状态。
- `baseline_results.json`及完整日志：包括PASS、FAIL、未完成与原厂预期非返回。
- 两次相同环境重建的BIN哈希一致；若不一致，先定位生成器、并行构建或非确定性来源。

建议归档：`evidence/reverse/reports/equivalence_remediation/<批次>/<项目>/`。路径与脚本名称是后续实施约定，不表示当前已全部存在。

## 5. S1：建立差异、定制与测试干预台账

建立以下台账，使用JSON或Markdown即可，先复用现有清单，不重复建立互相矛盾的事实源。

| 台账 | 必须字段 |
| --- | --- |
| 函数映射 | 原入口/范围、新符号/源码、调用者、ABI、内联/运行库替代说明、核对状态 |
| 差异台账 | ID、项目、原地址、源码位置、触发条件、观察差异、影响、证据、优先级、修复/验证状态 |
| 授权定制台账 | ID、用户需求、代码位置、允许改变的输出/状态、禁止扩散范围、专项用例 |
| 测试干预台账 | ID、脚本位置、原/新目标、hook或mask类型、输入输出、副作用、允许覆盖层次、替代验证 |
| 覆盖台账 | 原基本块/条件、适用输入、动态命中证据、未覆盖原因、后续动作 |

状态必须可区分：待确认、已复现差异、测试环境问题、授权定制、原版行为、已修复待验证、已闭环。不能只用“通过/未通过”覆盖全部事实。

差异优先级：P1=可能影响触发/保护/启停/闭环控制或关键持久化；P2=特定业务流程、通信或界面功能差异；P3=证据/注释/命名等低影响问题。优先级以已证实影响为准，不把每个地址注释错误都解释为实机故障。

### “金手指”线索逐项判定

检查常量强写、强制成功、临时调试开关、故障清零、保护禁用、输出固定值、认证写入、PC改写、R0覆盖、提前停止、跳过函数、mask、白名单、特殊期望和超预算处理。

这些只是线索。例如数值钳位可能是原版保护，volatile自赋值可能是原版访问，认证强制放行是本次要求保留的定制。**禁止根据关键词或自赋值外观直接改代码。**

## 6. S2：先消除验证失真

### 6.1 执行结果分类

| 结果 | 判定与处理 |
| --- | --- |
| `PASS_EQ` | 双方实际完成，满足原版兼容契约 |
| `PASS_CUSTOM` | 满足已授权定制预期；不得计为与原版完全相同 |
| `FAIL_DIFF` | 同一有效场景出现未授权的可观察差异 |
| `EXPECTED_NONRETURN` | 原版确为等待/自跳，验证到达预期路径和此前副作用；单独统计 |
| `INCONCLUSIVE_TIMEOUT` | 预算耗尽，不能判等价；定位等待点、循环条件和环境 |
| `WAIT_PERIPHERAL` | 缺少UART/ADC/I2C等有效输入，修正模型后重跑 |
| `OBSERVATION_ERROR` | hook/模拟器影响执行，必须换观测手段复核 |
| `UNREACHABLE_PROVEN` | 有调用域或控制流证据的不可达路径；保留证据，不算动态命中 |

动态摘要应满足：执行用例数=各互斥执行状态数量之和。静态不可达记录单独统计，不混入动态通过数。双方空调用序列单独计数，必须说明该帧为何应为空。不得把超时、异常、预算用尽、脚本退出0或“双方都没有执行目标”算作PASS。HardFault、非法访问等先归为失败或未决，不能未经定位就归咎于模拟器。

### 6.2 全面检查执行入口

- 审计公共run、execute_pair和所有直接emu_start调用，不只修公共函数。
- 正常函数必须确认返回哨兵；预期停在中间观察点时确认该点确实到达，不能仅因emu_stop被调用就成功。
- 用负向用例证明死循环、未就绪UART、错误种子、错误目标地址和缺少目标调用会被拒绝。
- 对ISR记录入口/返回约定；对原厂复位命令核对响应、EEPROM写入、进入自跳的顺序。离线自跳不能证明真实看门狗复位时间。

### 6.3 干预处理规则

| 干预 | 实施要求 |
| --- | --- |
| UART/ADC/I2C输入仿真 | 保留并显式建模；逐拍记录就绪/忙/错误输入，不能全局强制所有设备永远成功 |
| 跳过LCD、EEPROM等叶函数 | 可用于定位上层分支；记录调用、参数和必要副作用，并用独立叶函数测试及整合测试补齐，不声称全链路已执行 |
| 跳过纯空转Delay | 只用于逻辑验证；若延时包含喂狗、计数或轮询，不能整段跳过。延时计数、喂狗次数和模拟事件顺序另建专项；不以跳过后的结果证明真实耗时 |
| 改写PC/R0加速 | 限定到证据明确的空转区，说明被替代寄存器和内存；保留原业务判断及副作用，未替代部分必须真实执行 |
| GPIO位mask | 先保留未屏蔽差异，证明模拟器问题；通过无内存hook的末态、指令观测和独立外设序列交叉验证。不能因已有同名mask而沿用 |
| 字符串映射回原厂文字 | 仅验证原字形渲染路径。另以实际定制串执行并核对字形、列宽、单位和反显；这两类结果分别报告 |
| 忽略R0/临时SRAM | 根据真实ABI、调用者读取和副作用证明可忽略；不能成片忽略业务RAM或所有寄存器 |
| 强制业务成功/清故障/改反馈 | 不能用于受影响业务的验收；以真实场景和外设模型替代。保留认证放行的明确例外 |

清理干预意味着消除其对结论的污染，不要求物理删除所有hook。若取消某个hook后目标代码无法正确运行，先补模型，不能退回“比较两边中途状态”。

### S2门禁

全部验收入口均有执行完成检查；每项豁免和替身可追溯；负向测试有效；没有未解释的空跑、超时或大范围屏蔽；被隔离路径有明确后续整合任务。

## 7. S3：逐模块、逐关键分支核对

每个模块统一核对：物理地址→访问位宽/符号→条件边界→状态读写→调用参数与顺序→出口与共享尾部→后续拍影响。

| 顺序 | 范围 | 必查语义及场景 |
| --- | --- | --- |
| 1 | 闭环、ADC、输出级 | 两反馈槽使用不同种子；PID实参/积分/钳位；软起、软停、限流/限压进入与退出；通道切换；模式2；阈值前后及除数来源 |
| 2 | 启停、故障、继电器、ISR | 端子/面板/远程事件契约；急停优先级；故障置位/保持/清除；GPIO每次写的顺序/位宽；TIMER步进和EINT保持超时 |
| 3 | 参数加载与EEPROM同步 | 默认/有效/无效银行；高低字节；shadow/live方向；pending/retry门控；实际读写地址和值；重复同步和重启后恢复 |
| 4 | UART、Modbus | 帧态、间隙、超时、异常码回绕；站址/功能码/CRC/长度/数量；0x03/06/10独立语义；读后索引和非返回命令 |
| 5 | 状态机和显示 | MENU/ITEM/EDIT/KEY/超时组合；导航、编辑、保存、取消、共享尾；刷新与擦除时刻；非法枚举/项号/屏号；实际渲染与单位 |
| 6 | 启动、认证、GPIO、时钟 | 初始化顺序、CRP/向量、PLL/SCS/CLKOUT寄存器命名与访问；复用脚；认证放行不影响其它保护；启动失败路径 |
| 7 | 数据表、别名、运行库适配 | literal槽与被指地址区别；CRC/字符串/标定表；8位索引截断；同址别名；运行库替代是否保持调用契约 |

### 位宽与边界要求

不能因为高字节“通常为0”就把ldrb当ldr等价。分别验证实际允许输入域及异常初值；将高字节非0作为定向探针，再判断是否存在可达来源。不能用无意义的全随机RAM制造故障后直接认定正常使用受影响。

对8位输入能穷举时穷举0..255。对16/32位参数提取所有原比较阈值、取模/截断、零值、最大值、边界±1，并按模式/状态组合覆盖；有符号边界必要时包含0x7FFFFFFF/0x80000000/0xFFFFFFFF。

目标分支种子最后写入，并在执行前回读断言；同名字段或相邻字段必须用不同值，避免错地址碰巧一致。

### 覆盖口径

- 函数覆盖分母来自本项目原始清单；原业务函数全部归类，IAR运行库替代/内联有说明，不直接按“缺少符号”判遗漏。
- 控制/保护/持久化关键决策的所有分支出口必须有动态样本或充分不可达证明；未覆盖的可达出口不允许写“已消除该模块全部差异”。
- 条件组合不能只看整段被执行过；例如反馈复制测试必须命中具体store并检查PID消费后的状态。
- 编译优化造成新旧基本块不一一对应时，以语义路径和副作用映射，不能强求指令数或绝对PC相同。

## 8. S4：差异定位与修复闭环

每个缺陷执行以下步骤：

1. 保存修复前源码/ELF哈希、输入、外设事件及原始差异。
2. 排除错误入口、Thumb/SP/LR、初始RAM、ABI、别名和种子覆盖。
3. 找到最早语义分叉，定位原指令、literal值和源码，不只看最终报警或最终输出。
4. 将差异归类为真实还原缺陷、授权定制、原版行为、测试模型问题或观测伪影。
5. 提交最小补丁；修正必要注释，但不同时进行无关重构。
6. 运行最小反例、同类边界矩阵、受影响模块与跨模块场景，再跑项目完整门禁。
7. 用修复前版本反测回归；测试若不能区分错误版本与修复版本，补充目标命中/结果断言。
8. 更新差异ID和证据链接，记录影响范围：正常路径、特定模式、非法输入或仅验证工具。

闭环记录至少包含：原/新输入相同的证据、原指令依据、修复前失败、修复后通过、目标路径命中、观察结果、受影响相邻路径及剩余限制。

原厂看似多余的自写、额外读、空循环和寄存器残留分别判断。已证实的原厂怪癖保留并注释；不能用“优化”替代等价修复，也不能把所有怪癖都说成影响用户的缺陷。

## 9. S5：连续运行与跨模块验证

单函数一致后，在同一台仿真机中保留状态跨拍执行。两侧使用同一事件时间线，分别持有独立内存；每拍检查状态和外设事件，不在每拍重置RAM来掩盖累计误差。

必做场景：

| 场景 | 验收关注点 |
| --- | --- |
| 本地端子启动→稳定运行→停止 | 事件码、去抖、运行标志、继电器、输出封锁与斜坡 |
| 面板/远程/本地切换及连续按键 | 模式门控、手动给定、锁存、长按、切换当帧处理 |
| 闭环限流/限压进入→退出→再进入 | 反馈来源、积分历史、状态计数、限幅标志、恢复拍 |
| 启动或运行中故障/急停 | 响应优先级、故障保持、GPIO中间序列、故障清除后的允许状态 |
| 通信写参→运行→保存→重启加载 | 协议校验、活动值更新、EEPROM次数和顺序、重启恢复 |
| 菜单编辑→保存/取消→超时→返回 | 当前项、刷新/擦除、参数是否落盘及本帧尾计数 |
| 同步信号失锁→保护→恢复 | EINT/TIMER调度、保持窗口、输出安全态、重新允许条件 |
| 非法帧后接合法帧、断帧后重收 | 帧态恢复、缓冲区和长度、不得污染后续应答 |

中断组合采用先分析共享变量再设计有限调度：正常时序、临界读写前后插入ISR、连续同源中断及不同源交错。记录具体调度，不能以随机300次代替“所有中断交错已验证”。

随机差分需固定seed、明确合法状态约束并保存失败事件序列。发现差异先最小化；同时保存所有尚未分类反例，不靠换seed消除失败。

## 10. S6：模拟外设与时序契约验证

本阶段仍完全在代码和模拟环境内执行，验证外设模型、事件顺序及逻辑时间，不增加实机任务。

### 外设模型

- UART：区分发送就绪/忙、逐字节收帧、帧间隙和错误输入；记录每次寄存器访问及应答字节，避免以固定就绪掩盖轮询分支。
- ADC：输入通道和数据寄存器采用不同样本，覆盖完成位、采样序列、换算与反馈使用；不得用相同值掩盖错读地址。
- EEPROM/I2C：模拟ACK/NACK、字节内容、读写顺序、写周期忙；用持久介质镜像进行“结束一轮→重新初始化CPU/RAM→加载配置”的重启场景。
- GPIO与定时器：记录SET/CLR、置位宽度、匹配事件与清中断顺序；模拟同步信号存在、缺失、恢复和中断交错。
- 看门狗：区分正常喂狗和原厂等待复位路径；核对进入等待前的响应/持久化副作用。模型如未实现复位，不以到达自跳证明复位本身，结果限定为已确认等待契约。

### 时间与调度

使用明确的逻辑tick或虚拟事件时间轴，记录时间单位、外设事件、ISR插入点及停止条件。可以比较循环次数、喂狗次数、逻辑阈值与事件先后；不能把GCC/IAR指令数量或Unicorn运行墙钟时间直接当作真实微秒。

纯空转加速仅用于不依赖其耗时的逻辑样本；依赖延时或轮询的样本须单独运行受控模型，并明确其时间假设。未建立模型的路径标为未决，不强行计入通过。

### 交付与边界

交付模型版本/假设、事件序列、实际访问轨迹、预期停止契约及模型覆盖空白。本方案验收只对所声明的代码与模拟契约负责，不推导真实波形、控制环稳定性或所有硬件工况结论，也不以补做硬件测试作为本方案关闭条件。

## 13. 验收标准

满足以下条件才可写“本方案范围内差异已闭环”：

1. 两个项目原BIN哈希正确，源码与执行产物可复现。
2. 原函数全部归类，关键控制/保护/持久化分支全部有证据；可达但未覆盖项明确阻止相应模块全量关闭。
3. 未授权的已复现逻辑差异为0；P1/P2缺陷不存在“只改源码、没有有效回归”的关闭项。
4. 所有测试干预已分类；不存在未登记的业务强制值、宽泛mask或跳过目标路径的验收证据。
5. 正常路径实际完成，预期非返回、等待外设、超时和观测异常分列；本次关键验收没有未解释项。
6. 所有历史最小反例在错误版本有效失败，在修复版本通过；新回归有目标命中证据。
7. 授权定制逐项通过，特别确认认证放行保留，且没有扩展到急停、故障或输出保护。
8. 模块验证、跨模块连续运行、项目完整回归及模拟外设/时序专项通过；模型假设和未覆盖范围明示，关键模拟验收项无未解释失败。
9. 文档、索引、构建哈希和实际模拟加载镜像一致；剩余边界、原厂怪癖和模拟器局限明示。

“差异清零”必须带范围：具体源码版本、原BIN、输入域、覆盖路径、观察契约和定制清单。有限验证不写成“证明程序绝无bug”或“所有硬件工况完全等价”。

## 14. 实施分工、顺序与进度管理

| 阶段 | 执行角色 | 输出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| S0 | 实施者 | 两仓基线与可复现构建 | 输入与产物无歧义 |
| S1 | 实施者＋复核者 | 函数/差异/定制/干预台账 | 认证保留等边界明确 |
| S2 | 验证实现者＋复核者 | 可信运行器、模型与负向测试 | 不再将空跑或未完成算通过 |
| S3/S4 | 模块实施者＋复核者 | 证据化差异与最小补丁 | 高风险模块逐项关闭 |
| S5 | 集成验证者 | 可重放连续场景与调度证据 | 无未解释跨模块差异 |
| S6 | 模型实现者＋验证者 | 模拟外设/时序记录与模型假设 | 约定模型契约通过，空白已登记 |
| S7 | 交付复核者 | 最终报告、提交与代码交付清单 | 代码/模拟验收条款逐项有证据 |

角色可由同一实施者分时承担，但写修复与写验收理由不能互相替代证据；关键控制修复需再走一次独立原指令/执行复核。本文不要求自动启动并行代理。

排期以S0形成的实际分支/干预清单估算，不按“C文件数量”推算完成。每日记录已关闭差异ID、实际覆盖增量、未完成原因和下一步；不用测试数量增长代替进度。

第一批实施顺序：S0冻结 → 认证/定制与干预登记 → 完成门禁全入口检查 → 输出/反馈/启停/保护 → 参数与EEPROM → 通信 → 菜单/显示 → 连续场景 → 模拟外设与时序契约验证。
